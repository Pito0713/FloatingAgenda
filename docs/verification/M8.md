### codex 點名但未回報、由 Orchestrator 自行查證的五項

| 風險 | 結果 |
|------|------|
| **`.opacity(0)` 的圖示是否仍攔截點擊** | ⚠️ **成立，codex 漏了**。SwiftUI 的 `.opacity(0)` 不會關閉 hit testing，所以完整模式下右上角會有一個看不見、卻可點且擋住拖曳的 18×18 按鈕。**已修**：加上 `.allowsHitTesting(isVisible)` |
| `isCollapsed` 與 UserDefaults 的一致性 | ⚠️ 第一版用 `@State private var isCollapsed = AppSettings.shared.panelCollapsed` 鏡像，正是 M5 已經修過的同一類脆弱。**已改用 M5 的模式**：直接讀 `settings.panelCollapsed`，另留 `revision` 觸發重繪 |
| `inProgressEvent` 的邊界條件 | ✅ 條件是 `start <= now && now < end`：剛好等於 `start` 算進行中、等於 `end` 不算（避免行程結束瞬間還顯示）。空清單回 `nil` → 走「目前沒有行程」。跨日的整天行程只要涵蓋 `now` 就會被納入候選，但排在有時間的行程之後 |
| 切換時的高度同步 | ✅ 走的是 M1 已驗證過的 `setContentHeight`（保持 `maxY` 不變），收合是往上收。實測收合啟動時上緣精確等於存檔值 |
| 是否新增寫入路徑 | ✅ 沒有。收合模式的勾選呼叫的是同一個注入 closure → 同一個 `toggleCompletion` |

一條 CONFIRMED（來自 codex）＋兩項自行發現，全部已修。無 REJECTED、無 ESCALATE。

### 未能由機器驗證的項目（誠實揭露）

1. **點圖示切換的實際手感**：包含切換瞬間上緣是否真的不動、有沒有跳動。
   邏輯與 M1 已驗證的同一條路徑，但沒有實際點過。
2. ~~**收合後可拖曳的面積是否足夠**~~ → **使用者已驗收並回報「很難拖」，已追加修正**：
   頂部改成一條 24pt 的專用拖曳條（`PanelMetrics.collapsedDragStripHeight`），
   中間放一個常駐的小握把（Capsule 28×3，滑過時從 0.12 加深到 0.28）。
   加上 16pt 內距後頂部有 **40pt 全寬**可拖（僅右側 18pt 的箭頭除外），收合高度 128 → 142pt。
   握把刻意不做成 hover 才出現——使用者的問題正是「不知道哪裡能拖」，藏起來等於沒解決。
   codex 針對這次修正的審查回報「未發現問題」；Orchestrator 另確認
   `.allowsHitTesting(false)` 位於修飾子鏈最後（整條都不吃點擊），
   而箭頭是 overlay 的獨立圖層不受影響。
3. **完整模式的圖示 hover 浮現**：`ImageRenderer` 出的是靜態圖。
4. **收合模式的紅色錯誤行**：要製造寫入失敗才看得到，而紅線禁止我實際觸發寫入。

## 本里程碑自行決定事項

1. **收合模式不顯示日期標題**：使用者要的是「只顯示兩列」，加上 22pt 的大日期會讓收合失去意義。
   代價是收合後少了日期脈絡，改由頂部圖示列提供拖曳區。
2. **寬度維持 320pt**：不縮窄，這樣位置記憶與展開／收合之間的切換不會有水平跳動。
3. **收合內容獨立成 `CollapsedCardView`** 而非在既有 Section 裡加 `isCollapsed` 分支：
   收合的規則（取進行中、取第一筆、不套 6 筆上限）與完整模式差異夠大，混在一起會讓兩邊都難讀。
4. **圖示用 `chevron.up` / `chevron.down`** 而非 `rectangle.compress.vertical`：方向語意更直覺。
5. **`CollapsedCardView` 同樣不認識 `AgendaStore`**，所有互動注入，維持 `--snapshot` 的安全性。
