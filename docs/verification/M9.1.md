### snapshot 不變（§7.1 的方法有缺陷，已修正做法）

計畫 §7.1 要求「M9 開工前後，完整和收合模式的 snapshot 逐位元組一樣」，
做法是開工先存基準、之後再比。**照字面執行會得到假警報**：

```
基準（11:27，M9.1 前的 binary）vs M9.1 後（11:46）
  → 16 張裡有 9 張不同
```

但同一份 **M9.1 前的程式碼**在 11:46 重跑，跟 11:27 的基準比：

```
  → 同樣那 9 張不同（完全相同的檔名清單）
```

原因是卡片會渲染當下的日期與「進行中 · 至 HH:mm」，mock 的時間也是相對 `Date()` 算的，
所以 snapshot **只在同一個時間點附近可重現**（連跑兩次 16 張全同，實測確認）。
把基準存起來隔一段時間再比，比到的是時間差不是程式碼差。

**修正後的做法**：用 `git checkout-index` 把 M9.1 前的整棵樹抽到另一個目錄建置，
兩個 binary 在**同一分鐘內**各產一次圖再比：

```
M9.1 前的 binary vs M9.1 後的 binary（同一分鐘）
  → 16 張全部逐位元組相同 ✅
```

結論：M9.1 沒有動到任何畫面。後續 M9.2–M9.5 一律改用這個方法。

## 本里程碑自行決定事項

1. **「卡住的點」的判定偏離計畫 §5.2 的字面規則**。計畫寫「空的或以『無』開頭 → nil」，
   但那會把「無法連線到 API」這類**真的卡住**的描述誤判成沒卡住。改成：去掉第一個括號起的
   補充說明與結尾標點後，剩下的剛好是「無」才算沒卡住。「無」「無。」「無（…）」照樣正確
   判成沒卡住，而「無法…」會保留。真實資料已驗到這個差異（見上）。
2. **`ProjectStore` 自己持有 60 秒計時器**，而不是計畫 §5.2 寫的「跟著 AgendaStore 現有的
   60 秒計時一起」。理由：讓兩個資料層不必互相認識，`ProjectStore` 可以單獨測試，效果一樣。
3. **測試樣本不用 `Tests/.../Fixtures/sessions/` 檔案**（計畫 §5.1 列的路徑）。
   `SessionParser` 是純函式，用字串字面值就夠，而且不必在 `Package.swift` 加 resource 設定；
   讀檔那一側由 `ProjectStoreTests` 在 `temporaryDirectory` 底下建真實檔案樹來驗，測完刪除。
   兩條路徑都有覆蓋，而且不碰使用者真正的 `~/.agent-sessions`。
4. **`scan` 與 `read` 不標 `private`**：讓測試能同步驗掃描結果，不必輪詢非同步狀態。
   非同步那條路徑另有 `testRefreshPublishesScanResult` 覆蓋。
5. **燈號同時出現多個時取最嚴重的那個**（計畫未規定）：寧可把狀況講得比實際嚴重，
   也不要讓一個紅燈專案在清單裡看起來沒事。
6. **清單符號同時接受 `-` 與 `*`**（計畫只寫 `-`）：格式漂移時不該讓整份待辦歸零（§9 的容錯要求）。
7. **`ProjectStore` 加一道 scanner 注入縫**（Gate 3 新增）：唯一目的是讓世代守衛能被
   確定性地測試。沿用專案既有的 `ReminderWriter` 注入模式，production 路徑不變。
8. **`SectionState` 加條件式 `Equatable`／`Sendable`**（Gate 3 新增）：M7 當時刻意沒加，
   理由是「狀態指派造成的重繪成本極低」。M9.1 的情況不同——專案區的定時重讀在內容
   沒變時佔絕大多數，加守衛的收益明確。這個改動只是新增 conformance，
   `AgendaStore` 的行為完全不受影響。
9. **`--dump` 的燈號欄直接印 `statusText`**：它本身就含 emoji，再加一個解析出的燈號會變成
   「🟢 🟢 順暢」。只有 `statusText` 是空的才退回印解析結果。
