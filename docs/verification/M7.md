## Gate 3 Orchestrator 仲裁

codex 無發現。依「不全信也不全部忽略」逐一自查，並額外抓到一個 codex 沒提的問題：

| 風險 | 查證結果 |
|------|---------|
| 會不會停不下來 | ✅ `schedulePermissionPollIfNeeded` 先 `cancel()` 舊 Task，再 `guard needsAnyPermission else { return }`。權限拿到後狀態變 `.loaded`，不會再排下一輪 |
| 多個 Task 並存 | ✅ 每次呼叫都先取消舊的再指派，最多一個。`refresh()` 尾端與 `fetchReminders` callback 各呼叫一次，後者會取消前者 |
| 生命週期 | ✅ `deinit` 有取消、Task 用 `[weak self]`、`sleep` 後檢查 `Task.isCancelled` |
| 3 秒輪詢的成本 | ✅ 缺權限時 `loadEvents`／`loadReminders` 都被 guard 提前 return，`reloadCalendarLists` 也不會呼叫 `store.calendars(for:)`。每輪只有幾次 `authorizationStatus` 查詢 |
| 寫入路徑 | ✅ 未增加 |
| **（自行發現）無意義的重繪** | ⚠️ `@Observable` 不比對相等性，指派同樣的空陣列也會發出變更通知 → 缺權限時每 3 秒白重繪一次卡片。**已修**：`reloadCalendarLists` 加上相等性守衛。另確認 `setContentHeight` 本來就有 `abs(frame.height - height) > 0.5` 的守衛，所以不會每 3 秒重設視窗 frame 與陰影 |

無 CONFIRMED（來自 codex）、無 ESCALATE；一項自行發現並修正。

### 一個刻意不做的決定

若使用者永久拒絕權限，這個輪詢會每 3 秒持續跑下去。考慮過加上次數上限或改成
「只在使用者點過『打開系統設定』之後才快輪」，但結論是**不值得**：
加上相等性守衛後，每輪的實際工作只有幾次 EventKit 的 `authorizationStatus` 查詢
（行程內快取查詢）與兩次相等性比較，成本可忽略；而無上限的版本行為最單純，
永遠能在 3 秒內恢復。複雜度與收益不成比例。

2. **快速恢復輪詢的實際效果**：要製造缺權限狀態才能驗，而 PLAN §8 禁止我執行 `tccutil`。
   目前只有程式碼審查 ＋ codex 獨立審查。使用者下次重建後若又遇到授權重設，
   就能直接看到效果（按完允許後應在 3 秒內出現資料，而非最多 60 秒）。
3. **hover 底色與底線**：`ImageRenderer` 只能產靜態圖。
4. **深色模式在真實毛玻璃上的觀感**：snapshot 用的是不透明底色，真實面板是
   `NSVisualEffectView`，只有使用者看得到。

## 本里程碑自行決定事項

1. **README 加了 PLAN 未要求的兩節**：「設定項目」（UserDefaults key 表，方便用 `defaults write` 排查）
   與「專案結構」（含「Views/ 不認識 AgendaStore」的設計理由）。
2. **疑難排解以「重建後權限被重設」開頭**：這是使用者在本專案期間實際遇到兩次的問題。
3. **輪詢間隔取 3 秒**：比使用者從系統設定切回來的時間短，又不至於密集。
4. **相等性守衛只加在兩個陣列上**，沒有為 `SectionState` 加 `Equatable`：
   狀態指派造成的重繪成本極低，而 `setContentHeight` 已有守衛擋掉視窗層級的連帶開銷。
