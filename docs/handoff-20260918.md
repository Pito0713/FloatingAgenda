## 背景

原生小工具（WidgetKit）只能放桌面或通知中心、會被視窗蓋住、也沒辦法把行程和待辦合在一起。
所以改用 SwiftUI ＋ AppKit `NSPanel`（`.floating` ＋ `.nonactivatingPanel`）寫一般 App，
資料用 EventKit 讀，跟系統的行事曆與提醒事項 App 即時同步。

規劃在 2026-09-15 完成（`PLAN.md`），2026-09-16 到 09-18 實作完畢。
**專案已從 `~/FloatingAgenda` 搬到 `~/Floating`**，PLAN 內的路徑引用已同步。

## 重要決策

| 決策 | 選擇 | 原因 |
|------|------|------|
| 不走 WidgetKit | SwiftUI ＋ `NSPanel`（`.floating`、`.nonactivating`） | 原生小工具無法懸浮，也不能把行程與待辦合併 |
| 顯示範圍 | **只有今天**（行程 00:00–24:00；提醒＝逾期 ＋ 今天到期，無到期日不顯示） | 使用者 09-16 實測 7 天版後改的需求，PLAN §4.3／§4.4 已改寫為正本 |
| 行事曆識別 | 一律用 `calendarIdentifier`，**絕不用名稱** | 實測確認有兩個都叫「Family」的行事曆（分屬兩個不同帳號） |
| 篩選設定語意 | 存「**被隱藏的** ID」而非「顯示的 ID」 | 新增的行事曆會預設顯示。已被真實事件驗證：使用者期間新建的「採買清單」自動出現 |
| View 層與資料層的界線 | `Views/` 不認識 `AgendaStore`（唯一例外 `MenuBarView` 的篩選），所有互動都是注入的 closure | 讓 `--snapshot` **結構上不可能**寫入使用者資料 |
| 寫入路徑 | 整個專案**只有一個**：`AgendaStore.commitCompletion`（private，唯一呼叫端是可取消的 1.2 秒 Task） | PLAN §8 紅線：開發與驗證期間不得寫入使用者資料 |
| 預設位置取哪個螢幕 | `NSScreen.screens.first`（有選單列的主螢幕） | 實測 `NSScreen.main`（有鍵盤焦點的螢幕）會把卡片丟到副螢幕 |
| 毛玻璃圓角 | `NSVisualEffectView.maskImage`，`capInsets` 取 **2×** 半徑，`state = .active` | 不能用 SwiftUI `.clipShape` 裁 NSViewRepresentable；continuous 曲線延伸到半徑外，cap 取 1× 會被拉伸破壞；面板永不成為 key window，不設 `.active` 會一直是灰掉的外觀 |
| 收合模式放大 | 把字級與尺寸乘 1.25 後**取整**，不用 `.scaleEffect` | `.scaleEffect` 會把排版好的內容再縮放，文字落在非整數像素上發虛 |
| 純顯示文字 | 一律 `.allowsHitTesting(false)` | 否則會蓋住下層 `WindowDragArea`，卡片拖不動。**`.opacity(0)` 不會關閉 hit testing**，隱藏的按鈕要另外加 |
| 驗證方式 | 每個里程碑的 diff 都過 codex（異模型），發現逐條查證後三選一 | 制度鐵律「寫的人不驗收自己寫的東西」 |

## 已知問題 / 風險

- ⚠️ **ad-hoc 簽章導致授權會被重設**（PLAN §9 預告的風險，實際發生多次）：
  本機沒有簽章憑證，cdhash 每次重建都變，macOS 把重建後的 App 當新程式重新詢問授權。
  **影響**：每次 `build.sh` 之後，使用者第一次啟動可能要重新按「允許」。
  **解法**：README 疑難排解有 `tccutil reset Calendar|Reminders io.github.pito0713.floatingagenda`；
  長期解是用鑰匙圈自建簽章憑證（未實作）。
- ⚠️ **重建後第一次啟動可能很久才載入資料**：實測有一次停在佔位狀態**超過 30 秒**才自己恢復，
  而且當時畫面上**沒有**授權對話框。同一個 binary 重啟則是 0.3 秒就有資料。
  M7 加的 3 秒快速重試就是為這種情況設計的。診斷未完全收斂。
- ⚠️ **`build.sh` 會 `rm -rf build`**：使用者現在跑的就是那個 bundle，重建等於把它刪掉。
  重建前要先告知使用者，或勸他改用 `install.sh` 裝到 `~/Applications`。
- 🐛 **收合模式高度待確認（唯一未收斂的疑點）**：最後一次重開量到卡片 `320×102`，
  但預期是 160pt（當時行事曆裡有一筆到 15:45 才結束的行程，應該顯示為「進行中」）。
  102pt 表示至少有一列是短文字。**可能只是量得太早**（此前有三次同類誤判紀錄），
  但也可能是 `inProgressEvent` 在真實資料上沒選中。
  **重現／查證**：`--dump` 看有沒有「進行中」的行程，同時看卡片畫面那一列是不是「目前沒有行程」。
- ⚠️ **即時更新的三條路徑從未驗證**：`.EKEventStoreChanged` 的 0.3 秒 debounce、
  過午夜 `.NSCalendarDayChanged`、睡眠喚醒。因為紅線禁止改使用者資料、也無法模擬，
  只有程式碼審查 ＋ codex 審查。
- ⚠️ **測量陷阱（踩過四次）**：`open` 之後太早量面板高度會量到「載入中」的佔位值；
  `pkill` 不一定成功而 `open` 遇到還活著的 app 只會啟動它不會重啟；
  `.optionAll` 的視窗清單含未顯示視窗與 MenuBarExtra 的視窗；
  建置與測試並行會互相刪檔／殺行程。
  **對策**：用 scratchpad 裡預先編譯的 `growth2` 取樣到高度穩定，每步都斷言。
