### 從零補到 76 個測試

原本沒有任何測試。現在 `swift test` 約 1.2 秒跑完 76 個，涵蓋：

- `FormattingTests`：逾期判定、到期文案、行程時間文案的兩端邊界
- `OrderingTests`：行程與提醒排序
- `InProgressEventTests`：收合模式挑哪一筆、區塊標題
- `EventItemTests`：缺 identifier 時 id 的穩定性
- `AppSettingsTests`：透明度夾限與各項設定讀寫
- `CompletionTests`：**勾選完成的整條路徑**，含 `setRemindersState` 漏斗的四種情境

**每一批都用變異測試驗證過**（把歷史 bug 改回去，確認測試會失敗）。
這很重要：我曾寫出一個「整天優先」的測試**通過了卻證明不了任何事**——
那筆整天行程的 start 剛好也較早，規則整個拿掉也會通過。是 codex 審查測試本身時抓到的。

為了能測寫入路徑，EventKit 的寫入抽出了 `ReminderWriter` protocol：
production 用 `EventKitReminderWriter`（**整個專案唯一碰寫入 API 的型別，5 行、零判斷**），
測試注入 `SpyReminderWriter`。緩衝時間也改為可注入。
**測試從未實例化 `EKEventStore`，不可能寫入任何真實提醒。**

### 修掉「重建後卡在載入中數分鐘」

`start()` 原本把 `await requestAccessIfNeeded()` 排在最前面。ad-hoc 簽章每次重建讓
cdhash 改變 → TCC 重新評估 → 那個 await 實測要 30 秒到 4 分鐘以上，
期間**沒有資料、沒有 observer、連 60 秒計時器都還沒建立**，完全沒有重試機制。

改成先 `observeChanges()` → `startPeriodicRefresh()` → `refresh()` → await → `refresh()`。
實測同一情境：舊版 t=0.5s 是空白的「載入中」102pt 且數分鐘不變；
新版 t=0.5s 就顯示權限提示 186pt ＋「打開系統設定」按鈕，3 秒輪詢也已啟動。

## 重要決策（09-18 之後新增的）

| 決策 | 選擇 | 原因 |
|------|------|------|
| 第 10 條「取消入口消失但寫入照走」 | **維持現狀不修**（使用者 09-21 裁定） | 那個寫入是使用者自己點圓圈要求的，1.2 秒取消窗是便利性而非保證。改成「看不到就不寫」會讓「點完就切走」這個正常操作失效。已寫進 PLAN §4.4，避免之後被當 bug 重開 |
| 寫入路徑的防線 | 單一漏斗 `setRemindersState`，而非逐個出口補 | 「在每個出口記得清理」被證明四次都會漏 |
| EventKit 寫入 | 抽 `ReminderWriter` protocol | 唯一目的是讓勾選路徑可測；PLAN §8 禁止測試寫入真實資料 |
| 缺 `eventIdentifier` 時的 id | 用「行事曆 ID ＋ 標題 ＋ 起訖時間」，**不用 `UUID()`** | UUID 會讓每次重讀的 id 都不同，ForEach 識別漂移。殘留限制：所有欄位都相同的兩筆仍會撞號——刻意不修，用「陣列位置」補救會讓 id 又變回不穩定 |
| 收合模式的行程來源 | 進行中 → 沒有就取今天最近的一筆 → 都沒有才說「今天沒有行程」 | 使用者實際使用後回報：空檔佔一天大半，那一列只說「沒有行程」等於浪費兩列中的一列 |
| 收合模式的狀態與標題 | `featured` 回傳 `FeaturedEvent` 列舉而非 `EventItem?` | 標題直接由列舉決定，狀態與顯示不可能分歧 |
| `AgendaStore.start()` 的順序 | 重試機制**必須**排在權限請求之前 | 見上方說明。**不要把 `await requestAccessIfNeeded()` 移回最前面** |

## 已知問題 / 風險

- ⚠️ **ad-hoc 簽章讓授權會被重設**（PLAN §9 預告的風險，整個專案期間發生多次）：
  每次 `build.sh` 之後首次啟動，TCC 可能重新要求授權，且**不一定會彈對話框**，
  實測曾等待 4 分鐘仍未授權。`start()` 修好後至少會顯示「需要 X 存取權限」＋按鈕。
  長期解法（自簽憑證）寫在 README 疑難排解，未實作。
- ⚠️ **`build.sh` 會 `rm -rf build`**，重建前要告知使用者。
- ⚠️ **測量陷阱（我踩過五次，請務必注意）**：
  1. `open` 之後太早量面板高度會量到「載入中」的佔位值
  2. 「連續 N 秒不變＝穩定」的判定會把載入中誤判為最終值——**我因此發過一次假警報**
     （回報收合模式可能有 bug，實際上只是量得太早）
  3. `pkill` 不一定成功，而 `open` 遇到還活著的 app 只會啟動它不會重啟
  4. `CGWindowListCopyWindowInfo` 的 `.optionAll` 含未顯示視窗與 MenuBarExtra 的視窗，
     要過濾 `layer == 3` 且 `kCGWindowIsOnscreen`
  5. 建置與測試並行會互相刪檔／殺行程
  → **對策**：預先編譯取樣器、長時間觀察不早退、每步都斷言。
- ⚠️ **即時更新的三條路徑仍未驗證**：`.EKEventStoreChanged` debounce、過午夜、睡眠喚醒。
  因為紅線禁止改使用者資料、也無法模擬。
